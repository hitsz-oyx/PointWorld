先把四件事拆开。你现在最大的误区是：**黄色长轨迹虽然确实是模型输出，但 `t>10` 后它已经不是“PointWorld 根据 LIBERO 动作做出的预测”了。**

## 1. 黄色轨迹到底是谁的点流？

当前 Viser 中：

| 颜色   | 含义                                        |
| ---- | ----------------------------------------- |
| 蓝色   | 导出 clip 的 dense scene GT，多相机点云 union      |
| 绿色   | **模型实际预测的那批 scene points 的 GT**           |
| 黄色   | **PointWorld 预测的 scene point trajectory** |
| 粉/洋红 | GT scene point 的 (t\rightarrow t+1) 位移箭头  |
| 橙色   | robot/gripper point cloud                 |

黄色 `/pred_traj` 是直接对：

```python
pred_flows[tt]
    ->
pred_flows[tt + 1]
```

连线得到的。

因此黄色表示：

[
\hat P_{t,i}^{s}
]

即 **第 (i) 个场景点由 PointWorld 预测的位置随时间变化的轨迹**。

它不是：

[
F^r
]

机器人 point flow，也不是：

[
a_t
]

LIBERO 的 OSC action。

PointWorld 官方本身就把 robot action 表示为 **3D robot point flow**，然后预测 full-scene 3D point flow。

所以正确理解是：

[
\underbrace{F^r_{t:t+10}}*{\text{机器人动作条件}}
\rightarrow
\text{PointWorld}
\rightarrow
\underbrace{\hat P^s*{t:t+10}}_{\text{黄色}}
]

真正应该逐点比较：

[
\boxed{
\text{黄色 prediction}
\leftrightarrow
\text{绿色 GT}
}
]

而不是黄色和蓝色。

---

# 2. 为什么现在的黄色“长轨迹”不可靠？

注意我的措辞：

> **黄色确实是真实模型输出；不可靠的是 `--rollout > 1` 后构造给模型的条件。**

PointWorld release 的正式契约只有：

```python
RELEASE_CONTEXT_HORIZON = 1
RELEASE_PRED_HORIZON = 10
RELEASE_MIN_NUM_CAMERAS = 2
RELEASE_MAX_NUM_CAMERAS = 2
```

即一次：

[
P_t^s,F^r_{t:t+10}
\rightarrow
\hat P^s_{t:t+10}
]

所以 `--rollout=1` 的 11 帧黄色轨迹，才是一次标准 PointWorld forward。

当前 `--rollout > 1` 是你自己加的 autoregressive wrapper。

### 第一个问题：后续机器人运动不是 LIBERO action

当前代码对未来机器人 trajectory 做：

```python
linear
hold
repeat
```

例如 linear：

```python
new_traj = last + k * vel
```

然后：

```python
new_batch["robot_flows"] = _extrapolate_robot_traj(...)
```

所以第一段是：

[
a_t,\dots,a_{t+9}
\rightarrow
F^r
\rightarrow
\hat P^s
]

但第二段已经变成：

[
\text{假设机器人继续匀速}
\rightarrow
F^r_{\text{fake}}
\rightarrow
\hat P^s
]

它回答的是：

> “如果机器人按这个人工外推轨迹继续运动，PointWorld 会预测什么？”

而不是：

> “给定 LIBERO demo 中后续 action，PointWorld 能不能预测正确？”

这是最根本的问题。

---

### 第二个问题：新的 scene position 配了旧的 RGB-D

这比我上次说的 raw feature mismatch 更深。

PointWorld 的 scene encoder 会：

1. 从 RGB 用 DINOv3 提 feature；
2. 把当前 scene 3D point 投影进 camera；
3. 与 depth 做 visibility/depth consistency；
4. 给 3D point 采对应 image feature。

但 autoregressive 第二轮：

```text
scene_coord
= 第一轮预测后的物体位置

RGB
= 原始 t=0 RGB

depth
= 原始 t=0 depth

camera
= 原始 t=0 camera
```

例如一个碗已经被黄色预测抬起来：

```text
predicted bowl
      ↑
      ↑
table --------
```

但是 depth image 里面：

```text
bowl 仍然在桌面
```

模型会拿：

[
\hat p_i
]

投影到**旧 depth**。

于是：

[
z_{\text{pred}}
\neq
D_{\text{old}}(u,v)
]

scene encoder 的 visibility/depth consistency 就不再有真实几何意义。

所以 PointWorld release 不是简单的：

```text
point cloud -> dynamics
```

它实际还有：

```text
RGB-D observation
    ↓
DINO feature
    ↓
3D-to-2D projection
    ↓
scene encoding
```

这意味着真正的纯 autoregressive rollout 并不是简单：

```python
pred[-1] -> next input
```

就完成了。

---

### 第三个问题：robot coordinate 和 robot feature 冲突

当前：

```python
new_batch["robot_flows"] = extrapolated_robot
new_batch["robot_features"] = robot_features_orig
```

而 robot features 本身包含：

```text
robot_flows
robot_colors
robot_normals
gripper_open
robot_velocity
robot_acceleration
```

于是模型同时看到：

```text
robot_coord_seq:
机器人继续往前运动

robot_features.robot_flows:
机器人还是原始 demo trajectory

robot_velocity:
原始速度

robot_acceleration:
原始加速度
```

条件互相冲突。

---

### 第四个问题：t > 10 没有 GT

当前后续 GT 是：

```python
gt[:, -1:].expand(...)
```

即：

[
P^{GT}_{11}
===========

# P^{GT}_{12}

# \cdots

P^{GT}_{10}
]

实际上只是把最后一帧重复。

但随后仍保存：

```python
per_point_epe =
    norm(pred_np - gt_np)
```

因此 (t>10) 显示的所谓 EPE 是：

[
|\hat P_t-P_{10}^{GT}|
]

不是：

[
|\hat P_t-P_t^{GT}|
]

所以不能叫 EPE。

# 3. 那我到底应该怎么测“根据 LIBERO action 能不能预测正确”？

我认为应该把现在的 long rollout 删出主实验路径。

你真正需要的是：

## LIBERO action-conditioned sliding-window evaluation

对于 demo：

[
s_0,a_0,s_1,a_1,\dots,s_L
]

取任意 (t)。

### 条件分支

从：

[
s_t
]

开始真实执行：

[
a_t,a_{t+1},\dots,a_{t+9}
]

得到机器人实际轨迹：

[
F^r_{t:t+10}
]

也就是：

```text
LIBERO action
      ↓
controller + robot dynamics
      ↓
gripper / robot point trajectory
```

这是 PointWorld 所定义的 robot-action representation。

### GT 分支

从 HDF5 recorded states：

[
s_t,s_{t+1},\dots,s_{t+10}
]

恢复 rigid-body poses，构造：

[
P^s_{t:t+10}
]

于是：

[
\boxed{
(P_t^s,F^r_{t:t+10})
\xrightarrow{\text{PointWorld}}
\hat P^s_{t:t+10}
}
]

比较：

[
\hat P^s_{t:t+10}
\quad\text{vs}\quad
P^s_{t:t+10}
]

这就是你要的实验。

---

## 为什么条件和 GT 最好分开？

我建议：

```text
Condition:
action replay
    ↓
只提 robot_flows

GT:
recorded states
    ↓
提 scene GT
```

不要：

```text
action replay
    ↓
同时当 robot condition
和 scene GT
```

原因是 replay 可能有微小 divergence。

当前 exporter 已经计算：

```python
err = norm(
    current_state - target_state
)
```

但目前只打印 warning，仍继续导出。

我的建议：

```python
if max_replay_err > 0.01:
    raise RuntimeError(...)
```

这样你明确保证：

[
a_{t:t+9}
]

确实产生了与 demonstration 一致的 robot trajectory。

---

## 整个 demo 怎么看？

不要做现在这种：

```text
11帧预测
 ↓
把预测喂回去
 ↓
假设机器人匀速
 ↓
继续11帧
```

改成：

```text
window t=0:
s0 + action[0:10]
    -> predict 0:10

window t=10:
s10 + action[10:20]
    -> predict 10:20

window t=20:
s20 + action[20:30]
    -> predict 20:30
```

即：

[
t=0,10,20,\dots
]

每一段都是**严格合法的 PointWorld forward**。

Viser 可以增加：

```text
window start
[0] [10] [20] [30] ...
```

每个 window：

```text
黄色 = PointWorld prediction
绿色 = exact GT
```

这样你可以完整浏览整条 LIBERO demonstration：

> 抓取前预测准不准？
>
> 接触瞬间准不准？
>
> 抓住以后物体跟随准不准？
>
> 放置阶段准不准？

如果做定量，可以进一步 stride=1：

[
t=0,1,2,\dots,L-10
]

得到 horizon-wise EPE：

[
EPE(h),\quad h=1,\dots,10
]

这比一条人工 extrapolated 100 帧黄色轨迹有研究意义得多。

# 4. 现在的 5 相机视角设计怎么样？

我的结论很明确：

> **5 相机没有必要，而且当前 exporter、eval、schema、Viser 四者的 camera contract 已经不统一。**

现在 exporter 默认：

```text
agentview
birdview
sideview
frontview
robot0_eye_in_hand
```

但 schema 仍写：

```python
DEFAULT_CAMERA_NAMES = (
    "agentview",
    "robot0_eye_in_hand",
)
```

PointWorld release 固定 2 cameras。

eval 又从 5 个 camera 中 deterministic-random 选 2 个：

```python
selected_prefixes = rs.choice(
    camera_prefixes,
    size=2,
    replace=False,
)
```

于是不同 clip 的：

```text
model camera pair
```

甚至可能不同，因为 RNG 与 `__key__` 有关。

这会引入一个完全不必要的 camera-pair confound。

# 我实际算了一下当前 LIBERO tabletop 的视角覆盖

LIBERO tabletop workspace 定义：

```python
table_full_size = (1.0, 1.2, 0.05)
table_offset = (0, 0, 0.90)
```

当前 camera pose 中：

```text
agentview:
(0.659, 0, 1.610)

frontview:
(1.0, 0, 1.48)

birdview:
(-0.2, 0, 3.0)

sideview:
(-0.057, 1.276, 1.488)
```

agent/front 的实际 tabletop setup 与 arena camera 定义见 LIBERO 源码。

这些 camera 没有显式设置 `fovy`；MuJoCo perspective camera 默认 vertical FOV 是 (45^\circ)，水平 FOV 根据窗口尺寸自动计算。 ([MuJoCo][1])

按：

```text
320 x 180
table = 1.0 x 1.2 m
z ≈ 0.90 m
```

和源码 camera pose 做近似投影，我得到：

| Camera    | 桌面投影范围，约                      | 判断               |
| --------- | ----------------------------- | ---------------- |
| agentview | (u=-69\sim389,\ v=62\sim263)  | 近侧桌边大量出框         |
| frontview | (u=-46\sim366,\ v=113\sim238) | 与 agentview 高度冗余 |
| birdview  | (u=98\sim222,\ v=59\sim162)   | **完整覆盖桌面**       |
| sideview  | (u=6\sim272,\ v=89\sim187)    | **几乎完整，近边略裁**    |

这是基于源码 pose/table geometry 的几何近似推断；具体物体遮挡仍依 task 而变。   ([MuJoCo][1])

### 当前 5 个视角的问题其实很明显

```text
agentview
     \
      \       几乎同一 +x 方向
       frontview

birdview
    ↓         top-down

sideview
    ←         +y lateral

eye-in-hand
    moving
```

`agentview + frontview` 很冗余。

`eye-in-hand` 是动态近场 camera：

```text
适合看夹爪附近
不适合保证桌面全局 coverage
```

你明确说你的要求只是：

> **视角覆盖桌子。**

那么我的建议不是 5 个。

而是：

[
\boxed{
\text{birdview}+\text{sideview}
}
]

原因：

```text
birdview
    ↓
完整覆盖整个 tabletop
避免任何区域彻底缺失

sideview
    ↓
提供斜侧视角
补充 vertical surface / contact / height geometry
```

二者视角互补程度明显高于：

```text
agentview + frontview
```

而且都是 fixed cameras，不再引入 wrist camera 随机器人运动造成的 camera-pose 时变复杂性。

---

## 我建议现在直接改成这一套

`sample_schema.py`：

```python
DEFAULT_CAMERA_NAMES = (
    "birdview",
    "sideview",
)
```

`export_clip.py`：

```python
from .sample_schema import DEFAULT_CAMERA_NAMES

p.add_argument(
    "--camera_names",
    nargs="+",
    default=list(DEFAULT_CAMERA_NAMES),
)
```

然后 exporter 只输出：

```text
camera_0 = birdview
camera_1 = sideview
```

eval 的：

```python
min_num_cameras=2
max_num_cameras=2
```

保留。

因为只有两个 camera：

[
\text{available cameras}=2
]

模型一定拿这两个。

Viser 也只 fuse 这两个。

我还建议在 `.npz` 里直接保存：

```python
camera_names = np.asarray(
    args.camera_names,
    dtype=object,

```

否则现在：

```text

```

离开 exporter 后根本不知道对应哪个真实 camera。当前 schema 的 metadata 只保存 `__key__` 和 `point_object_names`。

**我的最终建议是：删掉当前 5-camera default；改成 `birdview + sideview`；主实验只跑 `--rollout 1`；然后做整条 LIBERO demo 的 11-frame sliding-window evaluation。**

这样黄色轨迹回答的才严格是：

[
\boxed{

PointWorld 能否预测正确的 scene point flow？}
}
]

这和你最初想做的事情完全一致。
