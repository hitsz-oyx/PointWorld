# PointWorld 在 LIBERO 上的微调指导

更新时间：2026-08-06

本文记录当前仓库的真实实现、已经确认的实验选择和下一步执行顺序。旧版文档中标为“待实现”的 LIBERO loader、微调权重加载、归一化统计和 native OSMesa 导出器现在都已经实现。

## 1. 已确认的第一版基线

- 初始化权重：`pretrained_checkpoints/small-droid/model-best.pt`
- 架构：保持 checkpoint 的 PTV3-small，不改网络结构
- predictor dim：128
- PTV3 patch size：256
- DINOv3：冻结
- 其余可训练参数：约 5110 万，全部微调
- scene point cap：12000
- robot point cap：500
- voxel size：0.015 m
- 相机：train 3 / val 3，顺序为 `frontview, sideview, birdview`
- workspace box：`[-0.8, -0.8, 0.65] -> [0.8, 0.8, 1.5]`
- 学习率起点：`3e-5`

暂不做 base/large、head-only warmup 或 DINO 解冻。先得到可信的 small-DROID 全量微调基线，再把这些作为独立消融实验。

## 2. PointWorld 官方训练数据的 stride

官方 `data` 分支中，DROID 与 BEHAVIOR 的默认切窗参数均为：

```text
frames_per_clip = 11
skip_every = 5
```

相关实现位于：

- `real/compute_2d_flows.py`
- `real/flow_2d.py`
- `simulation/behavior_3d_flows.py`

`skip_every=5` 表示在下采样后的时间轴上，每隔 5 帧建立一个新的 11 帧窗口。它不是窗口内部的跳帧数。

官方数据还有源数据时间下采样：

- DROID：`time_skip_ratio=2`
- BEHAVIOR：`time_skip_ratio=6`

这两个数字受原始数据采集频率影响，不应机械复制到 LIBERO。PointWorld 官方
checkpoint 的时间步是 0.1 秒，`H=10` 表示预测未来 1.0 秒。LIBERO HDF5 的
`control_freq=20 Hz`，原始 state 间隔为 0.05 秒，因此正式导出采用：

```text
frame_step = 2
11 个模型帧：s, s+2, ..., s+20
模型时间步：0.1 秒
总预测跨度：1.0 秒
窗口起点 stride：5 个模型时间步 = 10 个原始 state = 0.5 秒
```

相邻窗口仍重叠 6 个模型帧，但窗口内部不能使用连续的 LIBERO state。连续
`s...s+10` 只有 0.5 秒，与官方 checkpoint 的时序语义不匹配。

使用带内嵌 `model_file` 的官方 500 条 LIBERO Spatial demo，按每个 task
`45 train / 5 val` 数字顺序划分后，当前计划精确产生 5448 个窗口：

```text
train: 4900
val:    548
```

## 3. 数据划分与泄漏防护

必须先按完整 demo 划分 train/val，再从各 split 内切窗口。同一 demo 的窗口不得跨 split。
`bulk_export` 按 `demo_0, demo_1, ..., demo_49` 的数字顺序划分，默认每个 task
最后 5 条，即 `demo_45...demo_49`，进入 val。

推荐目录：

```text
/path/to/libero_pointworld_box_stride5/
├── train/
│   └── *.npz
├── val/
│   └── *.npz
└── manifest.json
```

`libero_npz` dataloader 已强制隔离 split。传入共享根目录时：

- train 只递归读取 `<root>/train`
- trainer 内部的 test loader 只递归读取 `<root>/val`，兼容 `<root>/test`
- 缺少 split 子目录时直接报错
- 显式 train/val 目录相同或互相嵌套时直接报错

标准方式是只传根目录：

```bash
--data_dirs /path/to/libero_pointworld_box_stride5
```

如果两个 split 不在同一根目录，也可显式传入：

```bash
--libero_data_dir_train /path/to/train \
--libero_data_dir_val /path/to/val
```

## 4. workspace box 与训练点

导出时使用 frame 0 的 world-frame box 选择点，并在 11 帧中保持相同点索引：

```bash
--workspace_bounds -0.8 -0.8 0.65 0.8 0.8 1.5
```

NPZ 会记录：

- `workspace_bounds`
- `workspace_crop_reference=t0_world_frame`
- 每个相机裁剪前后的点数

带有 `workspace_bounds` 的 LIBERO 样本会跳过官方 sphere crop，避免 box 后再次删减远离机器人的桌面点。voxel sampling 和 12000 点上限仍会执行，它们决定最终参与训练的点。

旧 NPZ 可以在不重新渲染的情况下迁移，且不会覆盖源数据：

```bash
python -m tools.libero.crop_npz_dataset \
  --input_root /path/to/old_libero_npz \
  --output_root /path/to/new_box_cropped_npz \
  --workspace_bounds -0.8 -0.8 0.65 0.8 0.8 1.5
```

旧数据每个 demo 只有 start=0 的一个窗口，只适合 smoke/过拟合检查，不适合作为正式训练集。
旧数据还使用连续 11 个 LIBERO state，只有 0.5 秒预测跨度。loader 默认要求
`frame_step`、`model_step_seconds` 等时序元数据，因此旧 NPZ 不会被误用于正式训练。

正式导出必须使用每条 demo 内嵌的 MuJoCo `model_file`。它记录 fixture 的模型级
位置，这些位置不在 92 维 flattened state 中。当前推荐数据源为：

```text
/home/u25s065008/datasets/libero/libero_spatial
```

`libero_regen_extended` 删除了 `model_file`，从 BDDL 重建时每次可能得到略有不同的
柜子、炉子等背景轮廓，不应作为正式几何导出的源。native exporter 默认对此报错；
`--allow_bddl_reconstruction` 只用于非严格预览。

## 5. 归一化统计

推荐将所有导出文件保存在一个数据池中，用 clip-level manifest 划分，避免复制：

```bash
python -m tools.libero.bulk_export \
  --libero_root /path/to/libero \
  --output_root /path/to/libero_pointworld_pool \
  --output_layout pool \
  [其他导出参数]
```

pool 模式将所有 clip 写入 `<output_root>/clips/`，不在导出时决定 train/val。
默认的 `split` 模式仍保留，以兼容旧命令。

```bash
python -m tools.libero.create_split_manifest \
  --data_root /path/to/libero_pointworld_pool \
  --train_demo_split /path/to/train_split.json \
  --val_demo_split /path/to/val_split.json \
  --output /path/to/libero_pointworld_pool/splits/paper.json
```

训练时使用同一数据根目录和 manifest：

```bash
--libero_data_root /path/to/libero_pointworld_pool \
--libero_split_manifest /path/to/libero_pointworld_pool/splits/paper.json
```

JSON 中 `splits.train` 和 `splits.val` 保存相对数据根目录的精确 NPZ 路径。
加载时会验证文件存在、路径不越界、split 无重复/重叠，并检查标准命名的同一 demo
不会跨 split。原有 `train/`、`val/` 目录参数仍然兼容。

stats 必须满足：

- 只读取 cropped train split
- 3 相机
- `grid_size=0.015`
- `max_scene_points=12000`
- 不读取 val

命令：

```bash
python -m tools.libero.compute_norm_stats \
  --data_dir /path/to/libero_pointworld_pool \
  --split_manifest /path/to/libero_pointworld_pool/splits/paper.json \
  --split train \
  --output stats/libero/norm_stats.json \
  --num_cameras 3 \
  --grid_size 0.015 \
  --max_scene_points 12000
```

这些参数现在也是脚本默认值，但正式实验仍建议显式写出，便于复现。输出目录中只能保留规范文件 `norm_stats.json`。

## 6. 微调语义

使用：

```bash
--finetune_from pretrained_checkpoints/small-droid/model-best.pt
```

它会：

- 继承模型结构契约和模型权重
- 不恢复 optimizer、step、epoch、best loss
- 不继承 DROID domain 和 DROID norm buffers
- 从 `--norm_stats_path` 初始化 LIBERO norm buffers
- 允许新数据域设置自己的 3/3 相机策略

`--model_path` 仍表示严格恢复训练，不能替代 `--finetune_from`。

## 8. 正式训练命令

正式 `frame_step=2 / stride=5` 数据和 train-only stats 准备完成后，先单卡做短程检查：

```bash
CUDA_VISIBLE_DEVICES=0 WANDB_MODE=disabled python train.py \
  --exp_name libero_small_box_step01_stride05_short \
  --seed 42 \
  --device cuda \
  --dataset_format libero_npz \
  --finetune_from pretrained_checkpoints/small-droid/model-best.pt \
  --domains libero \
  --data_dirs /path/to/libero_pointworld_box_stride5 \
  --norm_stats_path stats/libero \
  --train_min_num_cameras 3 \
  --train_max_num_cameras 3 \
  --eval_min_num_cameras 3 \
  --eval_max_num_cameras 3 \
  --base_lr 3e-5 \
  --batch_size 1 \
  --num_workers 4 \
  --eval_num_workers 2 \
  --max_train_steps 100 \
  --eval_freq 50 \
  --save_freq 50 \
  --disable_compile true
```

短程检查稳定后再决定单卡 batch size 和是否启用 4 卡 DDP。正式 DDP 模板：

```bash
torchrun --standalone --nproc_per_node=4 train.py \
  --distributed true \
  <其余参数>
```

不要在显存测试前直接沿用 checkpoint 的 `batch_size=22`；三相机输入的实际显存占用需要重新测量。

## 9. 正式实验顺序

1. 按 demo 固定 train/val split，先导出一个 task、每个 split 一个 demo 的正确时序数据。
2. 对小数据做 HTML 抽查，并验证同一窗口独立导出与 renderer 复用导出完全一致。
3. 导出 box-cropped 正式数据；一个 demo 的多个窗口复用同一个 LIBERO/MuJoCo 环境。
4. 只对正式 train split 计算 norm stats。
5. 随机抽样可视化 train 与 val，检查相机、box 和最终训练点。
6. 跑 100-step 单卡检查，确定显存、吞吐和 loss 稳定性。
7. 决定正式 batch size、GPU 数和训练 epoch/step 数。
8. 建立 zero-shot small-DROID 与 fine-tuned small-DROID 的同条件验证结果。

## 10. 下一处需要讨论的选择

批量导出现在已经按 demo 分组：每个 demo 只初始化一次环境和 renderer，再连续导出
该 demo 的全部窗口。内嵌 XML 下，独立进程导出与复用导出的同一窗口已验证为所有
NPZ 字段完全相等。

下一处需要讨论的选择转为训练资源配置：正式训练的 batch size、单卡/四卡方案和
训练长度，应在正确时序小数据的 2-step smoke 以及正式数据的 100-step 显存与吞吐
结果出来后再决定。目前不改模型架构。
